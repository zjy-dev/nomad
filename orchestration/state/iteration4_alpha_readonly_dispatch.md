# Iteration 4 Product Alpha Read-only Vertical Slice Dispatch

Status: APPROVED FOR DISPATCH AFTER THIS REVIEWED CONTRACT / LOCAL ALPHA ONLY / NON-PRODUCTION / NON-PILOT

## Review verdict

Current pre-review draft: `BLOCK`.

Reason: it assumed the current non-test Relay read path was safe enough for
dispatch and that the Gateway could decrypt or re-verify what it fetched. That
is not true enough to assign implementation safely.

This reviewed revision is the only approved dispatch contract. It approves one
real local Alpha slice with real processes, persistent SQLite, and a default
non-mock UI. It does not approve Pilot, E2EE, pairing, revocation, production
identity, or write/command capability.

## Why the previous draft was blocked

- The current non-test Relay read path is under-authenticated for this slice.
  `GET /v1/frames` and `POST /v1/ack` are device-scoped, but not Bearer-scoped.
  In local Alpha the device id is a fixed repo fixture, so device knowledge
  alone is not an acceptable reader boundary.
- The current non-test Relay read path does not return a signed envelope. It
  returns only `payload`, `flags`, `expires`, and `created`. A Gateway
  consumer cannot truthfully claim it re-verifies the Ed25519 envelope after
  `GET /v1/frames`.
- The current Relay envelope is explicitly TEST-ONLY Ed25519 integrity, not a
  production security envelope. This slice must not claim E2EE,
  confidentiality, or Pilot-ready transport.
- Therefore "Gateway fetches Relay bytes and decrypts or re-validates them" is
  not the minimum safe plan. It is both under-authenticated and semantically
  wrong for the current data shape.

## Approved minimal design

Deliver one real local read-only slice:

```text
Host projector -> POST /v1/frame -> Relay SQLite mailbox -> Gateway -> Mobile UI
```

The default Mobile path must use the real Gateway path and must not silently
fall back to `PilotSessionClient` or mock data.

Boundary:

- Relay binds loopback only and uses file-backed SQLite.
- The Host projector is a real process. It consumes Host authority and emits a
  bounded read-only projection frame.
- Gateway is a real process. It reads only the fixed local device stream,
  persists the last valid projection in durable local state, and serves the
  Mobile UI.
- Mobile default is non-mock and read-only.
- No `/v1/test/*`, fake OpenCode, Provider credential, Developer ID,
  SSHSIG/KRL, protected CAS, production supervisor, or command execution is in
  scope.

## Non-negotiable contract changes

### 1. Scope and claims

- This slice is `localhost` only, explicitly non-production, and explicitly
  not Pilot.
- It may claim only: real processes, loopback-only transport, persistent
  SQLite, default non-mock UI, Relay payload opacity, and Ed25519 ingress
  integrity at Relay write time.
- It must not claim: E2EE, production confidentiality, pairing, revocation,
  production auth, production identity, or independent Gateway envelope
  verification.

### 2. Relay payload contract

- `POST /v1/frame` remains the only writer path in scope.
- The payload carried by `/v1/frame` for this slice is already a bounded
  read-only projection generated by the Host projector. It is not an encrypted
  blob that the Gateway must decrypt.
- Relay stays content-blind: it stores opaque bytes, never parses projection
  JSON, and never imports Session or UI schema.
- If a future encrypted or E2EE envelope is desired, that is a separate
  security-envelope track and is outside this dispatch.

### 3. Relay read auth contract

- Local Alpha requires a dedicated local Bearer or equivalent capability token
  on non-test read routes used by the Gateway: `GET /v1/frames` and
  `POST /v1/ack`.
- If `GET /v1/ws` is retained, it must use the same local token. Otherwise it
  is out of scope for this slice; bounded polling is sufficient.
- The browser never receives this token.
- `POST /v1/frame` continues to rely on registered-device plus Ed25519 ingress
  verification; it does not become a Pilot or production auth claim.
- In `-alpha-local`, `/v1/devices/register` and `/v1/devices/deregister` are
  not part of the slice and must be disabled or hard-rejected.
- Gateway pins one configured local device id. It never accepts caller-supplied
  device selection.

### 4. Gateway contract

- Gateway does not decrypt Relay payloads and does not hold the device private
  key.
- Gateway hex-decodes payload bytes fetched from Relay, validates the bounded
  read-only projection schema, persists the last valid projection durably, and
  ACKs only after durable store succeeds.
- Gateway exposes only `GET /api/alpha/session` and optional
  `GET /api/alpha/session/:sessionId`.
- No `/api/pilot/*` route is used by the default UI.
- No POST command route exists in this slice. Any legacy command route must be
  removed from the default server or return stable `403 READ_ONLY_ALPHA`
  without contacting Relay.

### 5. Mobile contract

- Default UI constructs `HttpSessionClient` against `/api/alpha/session`.
- `demo=1` or `lab=1` remains the only mock path and must be visibly labelled.
- On network, decode, digest, or schema failure the UI renders `unavailable` or
  `unknown`. It must never silently switch to mock Live data.
- The browser receives only the read-only projection schema. It does not
  receive Relay tokens, device private keys, or decryption material.

## Minimal projection API

The Host-to-Relay wire payload and Gateway-to-browser response are distinct
contracts. The projector emits `nomad.alpha.readonly.host.v1` with top-level
`seq`, safe aliased metadata-only events, `changes` fixed to
`{"status":"unavailable","files":[]}`, and both provenance verification
flags set to `false`. This is the only honest state before Relay ingress and
Gateway validation have happened. The wire payload is bounded to the Relay
64 KiB payload limit.

After validating the Host wire digest and sequence, Gateway durably persists
the accepted Host record, then ACKs the Relay frame. It derives the browser
response below, sets both verification flags to `true`, maps Host `seq` to
`last_applied_seq`, and recomputes the response digest. The durable store may
be SQLite or an equivalently atomic file-backed implementation; this revision
uses SQLite with a full synchronous transaction.

Gateway response schema is `nomad.alpha.readonly.v1`:

```json
{
  "schema": "nomad.alpha.readonly.v1",
  "status": "available|unavailable|unknown",
  "session": {
    "session_id": "safe-id",
    "semantics_version": "1.0.0",
    "turn_state": "...",
    "host_connectivity": "...",
    "client_freshness": "...",
    "updated_at": "RFC3339"
  },
  "last_applied_seq": 12,
  "digest": "sha256:...",
  "events": [],
  "changes": {"status": "unavailable", "files": []},
  "provenance": {
    "source": "local-alpha-projector",
    "relay_ingress_verified": true,
    "gateway_schema_verified": true
  }
}
```

Rules:

- `events` and `changes.files` are bounded.
- Both Host wire and browser response `digest` values are `sha256:` plus the
  lowercase SHA-256 of UTF-8 canonical JSON for their respective complete
  object with only the top-level `digest` field omitted.
  Canonicalization recursively sorts object keys, preserves array order, and
  uses compact JSON separators.
- Gateway accepts any non-negative initial `last_applied_seq`. For the same
  session, a new projection must advance by exactly one. The same sequence and
  digest is an idempotent duplicate; the same sequence with another digest is
  a conflict; lower sequences are stale and jumps are gaps. Only a valid new
  projection or a durably present identical duplicate may be ACKed.
- Unsupported schema, gap, conflicting duplicate, stale projection, SQLite
  inconsistency, or decode failure returns `unknown` or `unavailable`.
- The response must not imply E2EE, Pilot, or production trust.

## Three implementation packages

### A1 — Relay local-alpha read boundary and durable mailbox

Owned files:

- `relay/server.go`
- `relay/protocol.go`
- `relay/mailbox.go`
- `relay/*_test.go`

DoD:

- `/v1/frame`, `/v1/frames`, and `/v1/ack` work without enabling `/v1/test/*`;
- Relay remains payload-opaque and never logs or parses projection content;
- local Alpha read routes require the dedicated local token;
- `-alpha-local` stays loopback-only and fixed-device only;
- device register and deregister routes are blocked in local Alpha;
- file-backed SQLite survives stop and restart with frame and ACK continuity.

Real verification:

- start Relay as a real process against a file-backed SQLite DB;
- POST signed projection frames;
- restart Relay and verify GET plus ACK continuity;
- prove `/v1/test/*` is not used;
- prove unauthenticated `GET /v1/frames` and `POST /v1/ack` fail in local Alpha;
- prove non-loopback `-alpha-local` start still fails.

### A2 — Host projector and Gateway read-only path

Owned files:

- Host-side projector or adapter module under the existing Host/testkit tree;
- `mobile-reference/pilot-gateway/relay-client.mjs`;
- `mobile-reference/pilot-gateway/server.mjs`;
- Gateway tests and projector tests.

DoD:

- projector emits bounded `nomad.alpha.readonly.v1` payloads and POSTs them to
  `/v1/frame`;
- Gateway uses only `/v1/frames` and `/v1/ack`, plus optional `/v1/ws` only if
  it is token-gated;
- Gateway does not decrypt, does not hold device private keys, and does not
  expose raw Relay payloads;
- Gateway persists the last valid projection before ACK;
- command routes are absent or stable `403 READ_ONLY_ALPHA`.

Real verification:

- run Relay, projector, and Gateway as separate processes;
- use the same persistent DBs across restart;
- fetch `/api/alpha/session` from the default path;
- verify identical projection continuity after restart;
- prove zero `/v1/test/*` and zero `/api/pilot/*` on the default path.

### A3 — Mobile default real-client wiring

Owned files:

- `mobile-reference/src/main.tsx`

DoD:

- default UI points to `/api/alpha/session`;
- default UI never silently constructs `PilotSessionClient`;
- commands are absent or disabled in Alpha;
- failure states render `unavailable` or `unknown`, never mock Live data;
- explicit mock mode remains `demo=1` or `lab=1` only.

Real verification:

- build the Mobile app;
- start real Relay and Gateway processes;
- load the default UI in a browser;
- prove the browser uses `/api/alpha/session`;
- prove the default path does not hit `/api/pilot/*` or `/v1/test/*`;
- stop and restart Relay, then verify the UI moves to `unavailable` or
  `unknown` rather than mock data.

## Execution order

1. A1 first. Freeze the non-test Relay local-alpha boundary and persistent
   SQLite behavior.
2. A2 second. Build the projector-to-Relay-to-Gateway read-only path on top of
   A1.
3. A3 third. Switch the default Mobile path to the real read-only Gateway.
4. Run one independent audit over A1, then A2, then A3. No P0/P1/P2 findings
   before calling the slice complete.
5. Record one content-free multi-process transcript with route paths, restart
   continuity, frame counts or digests, and zero-hit evidence for commands and
   test routes. Do not call it Provider evidence, Pilot evidence, pairing
   proof, revocation proof, or production readiness.

Pairing, revocation, production identity, Developer ID, SSHSIG, protected CAS,
and any write-capable mobile action remain external follow-up gates and are not
opened by A1-A3.
