# RT-001 provenance and hash rules

These rules are part of the preregistration contract. They prevent the
runtime spike from silently re-baselining, swapping fixture hashes, or
hiding a degraded result behind a different run configuration.

## 1. Fixture provenance

Every fixture used in the spike must have:

- A stable file name under `runtime-spike/fixtures/`.
- A `sha256` recorded in `fixtures/manifest.json`.
- A known upstream source or synthetic-generation script, recorded in the
  manifest's `source` field.
- A one-line `note` explaining why that specific fixture was chosen.

Fixtures are **additive-only** during RT-001. Existing fixture hashes
must not change. If a fixture must be re-generated, the new file goes
under a new name with a new hash, and the old file is retained until the
next preregistration.

### Fixture types

| Type | Purpose | Provenance rule |
| --- | --- | --- |
| `cold-start.json` | Startup fixture for `ws-cold-start` | Synthetic: generated by `scripts/gen_cold_start.py`. Hash frozen at preregistration. |
| `recovery-100k.json` | 100k-event replay for `ws-recovery-100k` | Synthetic: generated by `scripts/gen_recovery_100k.py`. Hash frozen. |
| `append-burst.json` | Append throughput fixture for `ws-append-durable` | Synthetic: generated by `scripts/gen_append_burst.py`. Hash frozen. |
| `long-session-8h.json` | 8-hour fixture for `ws-long-session-rss` | Synthetic: generated by `scripts/gen_long_session.py`. Hash frozen. |
| `ipc-roundtrip.json` | IPC fixture for `ws-sidecar-ipc` | Synthetic: generated by `scripts/gen_ipc_roundtrip.py`. Hash frozen. |
| `query-resume.json` | Query and cursor-resume payloads (used by `ws-recovery-100k`) | Synthetic: generated by `scripts/gen_query_resume.py`. Hash frozen. |

## 2. Measurement provenance

Every raw measurement file must record:

- The fixture file name and its `sha256`.
- The runtime binary or baseline reference, including its SHA.
- The command line that produced the measurement.
- The host hardware manifest (see §3).
- The SQLite PRAGMA dump at measurement time.
- The wall-clock start/end.

Measurements are **immutable** — a measurement file, once written, is
not edited. Corrections go into a new file with a new sequence number.

## 3. Hardware manifest

Every measurement must be tagged with a hardware manifest captured by
`runtime-spike/scripts/hardware_manifest.py`. The manifest must include:

| Field | Required |
| --- | --- |
| `hostname` | yes |
| `os` (Darwin/Linux/Windows + version) | yes |
| `cpu_model` | yes |
| `cpu_cores_logical` | yes |
| `cpu_cores_physical` | yes |
| `ram_mib` | yes |
| `storage_model` | yes |
| `storage_type` (NVMe/SATA/USB) | yes |
| `clock_speed_ghz` | no |
| `thermal_state` | no |

The manifest is stored as `hardware.json` next to the raw measurement,
and its SHA is recorded in the measurement's provenance block.

## 4. Hash rules

- `workload_set_hash` = `sha256(canonical_order_of_workload_ids + baseline_release + sqlite_pragma_dump)`.
  Computed by `scripts/compute_hashes.py` and written to `.prereports/preregistration.json`.
- `fixture_hash` = `sha256(fixture_file_contents)`.
  Computed by `scripts/gen_*.py` at generation time, recorded in `fixtures/manifest.json`.
- `hardware_hash` = `sha256(hardware.json)`.
  Computed by `scripts/hardware_manifest.py`.
- `measurement_hash` = `sha256(measurement_file)`.
  Recorded after each run.

Any change to the workload list, baseline release, or PRAGMA block
invalidates the `workload_set_hash` and requires a new preregistration.

## 5. Change protocol

To change any part of the preregistration:

1. Open a new `RT-001-revision-<n>` task.
2. Update `workloads/preregistered.yaml`.
3. Re-run `scripts/compute_hashes.py`.
4. Re-run `scripts/gen_*.py` for any fixture whose semantics changed.
5. Regenerate `.prereports/preregistration.json`.
6. Invalidate all prior raw measurements by appending a `superseded-by`
   field to each measurement file's provenance block.
