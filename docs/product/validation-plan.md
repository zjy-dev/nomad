# Nomad 验证计划

| 字段 | 内容 |
| --- | --- |
| 状态 | Draft 0.1 |
| 日期 | 2026-08-11 |
| 目标 | 在大规模开发前验证问题、交互、技术和付费四类风险 |

## 1. 验证顺序

风险按以下顺序处理：

1. 用户是否经常遇到问题。
2. 手机是否比现有替代方案更适合处理问题。
3. 用户是否会安装并持续使用。
4. 跨端协议是否能做到安全可靠。
5. 自有 Runtime 和 Rust 重写是否值得。
6. 谁愿意为什么付费。

前一项不成立时，不用后一项的好结果掩盖。例如 Rust 基准很好，不能证明移动产品有人要；原型很受欢迎，也不能证明远程审批已经安全。

## 3. 研究对象

### 3.1 招募配额

Discovery 计划招募 20 人，完成至少 15 次有效访谈：

| 互斥主分组 | 有效访谈目标 | 说明 |
| --- | ---: | --- |
| Claude Code/Codex 高频 CLI 用户 | 5 | 检验第一方 Remote 已解决多少问题 |
| OpenCode/Aider/Gemini CLI/其他 BYOK 用户 | 5 | 检验模型无关和开放性的价值 |
| SSH/tmux/远程工作站重度用户 | 3 | 比较通用终端和结构化移动端 |
| 近三个月放弃过 CLI Agent 的探索用户 | 2 | 避免只研究爱好者；单独分析，不计入 H1 高频样本 |

每人只计入一个主分组，总计至少 15 次有效访谈。“有代码数据边界”和“管理远程工作站”作为次级标签，不另算配额。额外招募用于补足临时取消和无效访谈，不改变主分组目标。

### 3.2 筛选条件

除“放弃用户”探索组外，主研究 cohort 必须满足：

- 每周使用 CLI code agent 至少三次。
- 最近两周至少有三次单任务运行超过十分钟。
- 能展示或描述最近一次真实任务，不只评价产品概念。
- 至少有一次任务包含代码修改或工具执行。

优先条件：

- 使用两种以上 Agent 或模型 Provider。
- 曾因离桌改变权限设置、使用远控或延迟任务。
- 管理远程工作站、家中主机或多台开发机。

排除：

- 只使用 IDE 补全，没有 Agent 任务经验。
- 只愿意讨论 AI 趋势，无法回忆具体工作流。
- 因保密限制无法提供任何行为层信息。

## 4. 研究方法

### 4.1 情境访谈

每次 45 分钟，尽量让用户展示最近一次真实 Session、终端历史、通知脚本或远控方式。先问过去行为，最后十分钟才展示 Nomad 概念。

访谈提纲：

1. 最近一次让 Agent 修改代码的任务是什么？从开始到结束发生了什么？
2. 任务持续多久？这段时间你一直在终端前吗？
3. 你离开后如何知道它是否还在运行？
4. 最近一次 Agent 等权限或问题时，你在哪里？等待造成了什么后果？
5. 你现在用 tmux、SSH、远控、通知脚本、auto-approve 或云 Agent 解决什么？
6. 哪些操作你绝不会从手机批准？为什么？
7. 你如何审阅 Agent 改动？手机上至少需要看到什么，才敢让任务继续？
8. 代码、命令和 diff 经过第三方中继时，你有哪些顾虑？
9. 如果电脑休眠、网络断开或 App 显示旧状态，你期望系统怎么说？
10. 如果只保留一个能力，通知、回复、审批、diff 和 Stop 中你选哪个？
11. 你是否愿意安装常驻 daemon？什么会让你拒绝？
12. 展示原型后：哪些地方与你当前工作方式冲突？

禁止使用“你会不会用”作为主要证据。记录最近发生频率、替代方案成本和用户已经采取的行为。

### 4.2 一周日记研究

从访谈对象中选择 8 人。每次启动超过五分钟的 Agent 任务时记录：

```text
日期/时间：
Agent 与模型：
任务目标：
预计时长 / 实际时长：
是否离开电脑，多久：
离开时 Agent 状态：
期间是否等待权限、问题或报错：
如何得知：
使用了什么替代方案：
回到电脑前浪费了多少时间：
如果手机能处理，当时需要哪些信息或操作：
```

研究者每天只做一次轻量提醒，避免要求用户为每个 Token 记录。周末进行 20 分钟回顾，核对记忆与日志差异。

H1 通过线：

- 8 人中至少 5 人一周内记录过等待或状态不明。
- 所有参与者合计至少 12 次可由跨端控制改善的事件。
- 至少一半事件造成五分钟以上等待、回桌或放宽权限。

H1 停止线：

- 事件主要发生在低频用户，目标用户普遍已有满意方案。
- 大多数长任务实际运行在云端，不依赖本机在线。
- 用户离桌时有意不希望任务继续，手机控制没有价值。

### 4.3 可点击原型测试

使用高保真但无真实执行的原型，测试五个任务：

1. 找出哪个 Session 需要你处理。
2. 判断一条 `npm install` 或网络请求是否可以允许。
3. 拒绝一条工作区外写入，并说明原因。
4. 发现 Agent 方向不对，停止当前步骤并补充指令。
5. 网络中断后判断当前内容是否可信，再恢复查看 diff。

每个任务记录完成率、时间、误触、犹豫点和用户复述。Approval 测试必须包含 benign、ambiguous、dangerous 三类操作，以及 Unicode/长命令等呈现边界。

H2/H3 通过线：

- 85% 任务无需主持人帮助完成。
- 90% 用户能正确区分 Live、Stale 和 Offline。
- benign/dangerous 操作判断准确率至少 90%。
- 没有用户把模型解释误认成系统保证。
- 至少 70% 用户选择结构化页面为默认入口，raw terminal 只作应急。

高风险误批准一例就不是“平均准确率可接受”。需分析呈现或规则后重测。

## 6. 技术验证设计

### 6.1 测试矩阵

| 维度 | 条件 |
| --- | --- |
| 网络 | Wi-Fi→5G、5G→Wi-Fi、飞行模式 30 秒、10% 丢包、500ms RTT、乱序和重复包 |
| 手机生命周期 | 前台、后台、系统 kill、重启、Push 关闭、低电量模式 |
| Host | Connector restart、OpenCode restart、sleep/wake、网络切换、磁盘满 |
| Relay | 连接重置、区域故障、延迟 Push、重复 Push、密文事件延迟和重排 |
| 多设备 | 两台手机同时 allow/deny、桌面先处理、设备刚被吊销 |
| 数据 | 10 万事件、100 文件/1 万行 diff、超长日志、二进制文件、Unicode/bidi |
| 安全 | QR 重放、旧 approval 重放、action 变化、Relay 数据库泄露、恶意 Prompt |

### 6.2 一致性不变量

自动化和故障注入必须持续验证：

- 同一 Session 的 durable `seq` 严格递增。
- 同一 `request_id` 最多启动一次 Host 工具执行；崩溃窗口内结果不明时进入 `OutcomeUnknown`，不自动重跑。
- Permission 只有 OpenCode 一套 pending 状态，并从 pending 原子地进入一个终态；手机、桌面竞争时只接受一个结果。
- Connector 事件投影必须与 OpenCode Host 快照收敛一致；Runtime Alpha 的事件和投影才要求同事务成功或失败。
- 客户端显示 Live 前，已应用 seq 与快照一致。
- 被吊销设备不能提交新命令，也不能解密新轮换密钥。
- Connector 或 OpenCode 重启后不自动重跑状态不明的可写工具。
- 瞬时 delta 丢失不改变最终 durable message。

### 6.3 Rust 基准纪律

- 实验开始前登记 3 至 5 个产品相关 workload、权重、目标和允许退化预算。至少包含冷启动、10 万事件恢复、长 Session RSS 和 durable event append。
- 固定 OpenCode release，不用源码开发模式对比 release binary。
- Rust、Go 或其他候选必须使用相同 SQLite PRAGMA 和 durability。
- Provider 使用本地可重放 mock，真实 Provider 延迟另报。
- 报告 p50、p95、p99、CPU time、peak RSS、allocation、I/O bytes。
- 冷启动和常驻 daemon 分开测。
- macOS、Linux、Windows 分开报告，不合并成一个数字。
- 原始结果和 fixture 进入仓库，营销文案不得挑选单次最好成绩。

## 7. 指标字典

| 指标 | 定义 | 排除项 |
| --- | --- | --- |
| 合格用户 | 符合 3.2，并至少完成一个本地 Session | 团队成员、只打开 App 的人 |
| 跨端激活 | 首个 Session 中另一设备的 reply、approval、deny 或 Stop 被 Host 接纳 | 只看通知、只打开列表、Relay 仅收到 |
| Durable progress | Host 接纳远程操作后出现新的 `message.completed`、`tool.started`、`tool.completed`、有效内容变化的 `diff.updated` 或 `turn.completed` | `message.accepted`、ack、presence、标题/metadata 更新和重复投影 |
| 远程推进 Turn | Reply、纠偏或 allow 被 Host 接纳，之后出现 Durable progress，并进入 Completed、Cancelled 或 Failed | Stop、deny、`OutcomeUnknown`、恢复失败、演示 Session |
| 远程止损 Turn | Stop 或 deny 被 Host 接纳并产生 Cancelled 或明确拒绝结果 | Relay 仅收到、结果未知 |
| 合格阻塞 | Host 在线时产生，属于手机允许处理范围的 Question 或 Permission | 必须回桌面的 shell/高风险操作；忽略和过期不能排除 |
| 无需回桌解除率 | 被手机处理后产生后续进展或明确安全终止的合格阻塞数 / 全部合格阻塞数 | Host 在阻塞产生前已离线 |
| 自动恢复机会 | 故障注入开始于 Live 客户端；网络恢复后 10 秒内与 Host 快照一致且无未知 gap 即成功 | 不允许对同一事件 trace 重复计数制造分母 |
| 真实恢复成功 | 真实连接从 Live 中断后，网络恢复 30 秒内与 Host 快照一致且无未知 gap | Host 确实关机、用户删除数据；每次排除需记录原因 |
| 第 N 周留存 | 激活 cohort 在第 N 个七天窗口内完成至少一个远程推进 Turn 或远程止损 Turn | 仅收到 Push、`OutcomeUnknown` |
| 误审批 | 用户报告不符合意图，或系统发现展示动作与实际动作不一致 | 用户后来改变主意但展示正确 |
| Crash-free Session | 未发生 Runtime 或 App crash 的 Session / 全部 Session | 用户主动 Stop、Provider 正常错误 |

## 8. 分析方法

- 每个 cohort 固定按激活周观察，不混用累计 MAU。
- 区分 Claude/Codex 第一方 Remote 用户与开放 Agent 用户。
- 区分远程工作站、笔记本和桌面主机，Host 在线条件不同。
- 同时报中位数和 P95，不用平均值掩盖弱网尾部。
- 可靠性失败逐次复盘，不等样本足够再处理。
- 自动故障注入、八小时恢复和真实用户恢复分别报告，不混合分母。99.5% 只在至少 600 次预登记独立机会后作为候选门槛。
- Push 分别报告 Provider 接受、App receipt/前台校准、阻塞产生到 App 首次确认时间。APNs 不提供的系统展示回执不伪造。
- 访谈结论保留反例和原话上下文，不只整理支持产品的观点。
- 价格实验使用真实付款；Van Westendorp 等问卷只作候选区间，不作商业验证。

## 9. 每周决策节奏

| 时间 | 会议 | 输出 |
| --- | --- | --- |
| 周一 | Reliability review | 上周断线、恢复、Push、Crash 和安全事件 |
| 周三 | Research review | 最新访谈、行为和假设变化 |
| 周五 | Scope review | 实验进度、阶段门、删减和下周计划 |
| 阶段末 | Go/no-go | 一页书面决定，更新 decision log |

任何团队成员可以因安全不变量失败要求停止扩量。产品负责人不能用留存指标覆盖安全停止条件。

## 10. Discovery 完成模板

阶段结束时只回答以下问题：

```text
我们观察到的高频问题是什么？
哪类用户最痛，发生频率是多少？
他们今天如何解决，已付出什么成本？
```
