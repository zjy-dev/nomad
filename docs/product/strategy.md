## 1. 执行摘要

Nomad 是一个 local-first code agent runtime。用户主要在命令行中发起开发任务，仓库原件、Provider 凭据和工具执行默认留在自己的电脑上；为完成推理，Runtime 会把选定的指令、代码片段和工具结果发送给用户选择的模型 Provider。手机是同一会话的另一个客户端，用来查看进度、回答问题、处理允许远程批准的操作、审阅 workspace diff 和停止任务。

市场已经有大量 CLI Agent。Claude Code、Codex 和 Cursor 也在补移动或云端控制能力。单做“更快的 OpenCode”没有足够的产品差异。Nomad 的机会是把以下条件放在一个产品里：

- 模型无关，而不是绑定单一模型账户。
- local-first，而不是要求把仓库迁到托管沙箱。
- 移动端是正式控制面，而不是浏览器终端。
- 长会话可恢复，多设备状态一致，弱网下不重复执行操作。
- Runtime 和自托管链路可审计，托管中继看不到代码正文。
- 本地资源占用有明确指标，不用“高性能语言”代替性能证据。

初期采用双轨策略。两条轨道先共同冻结不依赖信任模型的 Session Semantics v0；产品轨用 OpenCode adapter 快速验证跨端需求，内核轨用 Rust 原型验证启动速度、内存和持久化。两条轨道分别设停止条件。安全架构另设真实仓库外部测试前必须通过的阶段门，并在信任与密钥模型确定后冻结 Security Envelope v0。

## 2. 用户问题

Code agent 把一次开发工作从几分钟的人机对话，变成了持续几十分钟甚至更久的任务。当前 CLI 工作流仍假设用户一直坐在终端前：

- Agent 等待一项权限时，用户不在电脑旁，整个任务就停住。
- 用户无法快速判断 Agent 是在工作、报错、跑偏，还是已经完成。
- SSH、tmux 和移动终端能重新接入 shell，但不适合阅读长 diff、结构化审批和测试结果。
- 云 Agent 允许用户关掉电脑，却要求迁移代码、凭据和运行环境，成本和隐私边界都不同。
- 现有开源 Agent 的网络接口通常要求用户自己处理端口、TLS、VPN 和鉴权。
- 长会话的断线恢复、事件补发和多设备一致性常被当作 UI 细节，最终出现重复审批、状态过期或消息丢失。

问题不在于“手机上没有终端”，而在于 Agent 会话还没有成为独立、持久、可安全控制的产品对象。

## 3. 愿景与使命

### 愿景

开发任务不再被某一个终端连接拴住。

### 未来 24 个月的使命

做出一个可信的本地 Agent runtime：开发者可以从命令行开始工作，在任何已授权设备上继续掌控同一会话，不必迁移仓库，也不必把远程 shell 暴露到公网。

### 一句话定位

Nomad 是给 CLI 开发者使用的 local-first code agent：任务在电脑上运行，人在手机上也能安全地继续推进。

## 4. 产品原则

### 4.1 本机是默认执行环境

Agent 默认使用用户已有的仓库、依赖、凭据和算力。Nomad 云端只负责设备发现、密文路由和推送，不执行代码，也不持有会话内容密钥。用户选择的模型 Provider 是独立的数据接收方，推理所需上下文会按其条款发送。以后可以增加远程 runner，但不能让它反向污染 local-first 的默认体验。

### 4.2 同步会话，不镜像终端

手机收到的是消息、工具调用、权限请求、测试结果、diff 和状态事件。PTY 只作为后期的高级逃生入口。这样才能在断线后恢复、在小屏上审阅风险，并限制移动端权限。

### 4.3 手机只承载适合手机的决定

手机适合确认、纠偏和止损，不适合长时间编辑代码。每个移动功能都要回答一个问题：它是否能让用户在两分钟内推进任务？如果不能，默认不进入首版。

### 4.4 性能必须可测

Rust 不是卖点本身。Nomad 只宣传用户能感知、可以复现的数据，例如冷启动、空闲内存、十万事件回放、断线恢复和长会话稳定性。模型推理和依赖安装不归因于本地语言。

### 4.5 安全决策由本机最终裁决

手机提交的是签名决定。本机在执行前重新校验会话、参数、工作目录、版本和有效期。中继不能伪造审批，也不能将一项旧审批重放到新的命令上。手机只允许批准可被确定性呈现的结构化工具和命令白名单；任意 shell、脚本和动态下载必须回到本机处理。

### 4.6 开放建立信任，托管购买便利

CLI、Runtime、协议和自托管中继应尽量开放。商业收入来自托管连接、推送可靠性、多设备历史、团队策略和企业管理，而不是锁住本地会话格式。

## 5. 目标用户

### 5.1 首要用户

高频使用 CLI Agent 的独立开发者和小团队工程师。他们符合大部分特征：

- 每周使用 Claude Code、Codex、OpenCode、Aider 或类似工具三次以上。
- 任务常包含编译、测试、搜索和多文件修改，单次耗时超过十分钟。
- 会在开会、通勤、吃饭或处理其他工作时离开电脑。
- 愿意使用 BYOK，关心代码和凭据是否离开本机。
- 熟悉终端，但不愿在手机上操作完整 shell。
- 能容忍早期产品的安装和诊断成本，愿意反馈协议与兼容问题。

首批用户优先从基础设施、后端、全栈和开源维护者中招募。这些用户的长任务和 CLI 使用密度更高，问题更容易被观察到。

### 5.2 次要用户

- 同时管理多台开发机或远程工作站的个人开发者。
- 有本地数据边界要求、无法使用公共云 Agent 的企业工程团队。
- 希望通过统一客户端控制多个 Agent runtime 的高级用户。

### 5.3 暂不服务

- 想在手机上完成主要编码工作的用户。
- 不使用终端、只依赖 IDE 内联补全的开发者。
- 需要无人值守云任务、电脑关机后仍继续执行的用户。
- 首版就需要多人结对、经理审批链或大规模 Agent 调度的团队。
- 无法接受安装本地 daemon 的受管设备用户。

## 6. 核心 Jobs to Be Done

| 场景 | 用户想完成的事 | 当前替代方案 | 期望结果 |
| --- | --- | --- | --- |
| 离开电脑 | 当任务继续运行时，我想知道 Agent 是否正常推进 | 回电脑看终端、SSH、tmux | 两秒内看到可信状态和最后活动时间 |
| 等待权限 | 当 Agent 被权限卡住时，我想在手机上理解风险并处理 | 回电脑、开移动终端、全量 auto-approve | 十五秒内安全地允许一次或拒绝 |
| 任务跑偏 | 当 Agent 理解错方向时，我想补一句指令或立刻停止 | 等它完成、远程 shell 发中断 | 指令状态可追踪，停止操作不重复执行 |
| 审阅结果 | 当任务完成时，我想快速判断改动是否值得回到电脑继续处理 | 在通知里看一句总结、打开 GitHub PR | 按文件查看 diff、测试和错误摘要 |
| 网络切换 | 当手机从 Wi-Fi 切到蜂窝网时，我想继续同一会话 | 重新登录、重新 attach、猜状态 | 自动补齐事件，明确显示 Live 或 Stale |
| 保护代码 | 当我跨网络连接时，我想避免平台读取仓库内容 | 开 VPN、自建 tunnel、接受云端可见 | 中继只持有密文和最少路由元数据 |

## 7. 市场定位

### 7.1 竞争参照

| 类型 | 代表产品 | 优势 | Nomad 不直接复制的部分 |
| --- | --- | --- | --- |
| 单厂商本机远控 | Claude Code Remote Control、Codex Remote | 第一方账户和客户端体验完整 | 不绑定单一模型或订阅账户 |
| 云端 Agent | Cursor Cloud Agents、Codex Cloud、GitHub Copilot | 电脑可关机，易于并行 | 首版不承担云环境和代码托管成本 |
| 开源 CLI Agent | OpenCode、Aider、Gemini CLI、Goose | 模型选择和扩展性强 | 不用功能数量竞争，不复制完整 Provider 生态 |
| 移动远控封装 | Happy | 提供手机接管和 E2EE 的供给侧先例 | 不长期依赖其他 CLI 的内部交互层 |
| 远程终端 | Termius、Mosh、tmux | 通用、成熟、可处理紧急情况 | 不把 TTY 当作主要移动界面 |

### 7.2 差异化顺序

1. 跨端会话可靠性：事件有序、可回放、可恢复，审批和中止具备幂等语义。
2. 移动端安全交互：命令、影响范围和 diff 由本机生成并签名，手机适配小屏决策。
3. 开放且模型无关：支持 BYOK、自托管中继和公开协议。
4. 本地效率：单二进制、低空闲资源、长会话不持续膨胀。

高性能语言排在第四位。前三项做不好，启动快几十毫秒没有产品意义。

## 8. 切入点与扩张路径

### 8.1 初始切入点

只解决一个闭环：用户在电脑启动任务，离开后在手机上解除一次允许远程处理的真实阻塞，并看到 Host 接纳决定后产生新的进展。

这个切入点具备几个优点：

- 发生时用户有明确痛感，价值可以用节省的等待时间衡量。
- 不要求首版支持手机写代码。
- 权限、推送、断线恢复和状态同步会迫使团队把底层协议做对。
- 可以先接入 OpenCode 验证需求，再替换成自有 runtime。

### 8.2 扩张顺序

| 阶段 | 扩张内容 | 前提 |
| --- | --- | --- |
| 1 | 手机查看、审批、补充指令和 Stop | 跨端会话闭环可靠 |
| 2 | 从预批准 workspace 远程发起任务 | 设备、权限和 worktree 隔离成熟 |
| 3 | 支持 ACP 等本地 Agent adapter | 内部事件协议稳定，有明确用户需求 |
| 4 | 团队策略、审计和自托管控制面 | 个人版留存和企业设计伙伴成立 |
| 5 | 可选远程 runner 或托管沙箱 | local-first 主路径没有被稀释 |

## 9. 产品支柱

### 9.1 CLI Runtime

一个可独立分发的 Agent runtime，负责会话、模型调用、工具执行、权限和持久化。它是原生内核与安全阶段门通过后的产品阶段，不属于最先交付的 Validation Companion。首个 Runtime Alpha 只实现高频闭环，不追求 Provider、插件或 IDE 数量。

### 9.2 Session Protocol

CLI、TUI、手机和 Web 都是同一 Session owner 的客户端。协议包含持久事件、瞬时流式增量、游标恢复、命令幂等和状态快照。Validation Companion 的 Session owner 是固定版本的 OpenCode 加 Nomad Host Connector；自有 Runtime 成熟后再接管。协议是两条路径共用的产品资产。

### 9.3 Mobile Companion

围绕五件事设计：看状态、处理阻塞、补充指令、看改动、停止任务。公开测试版前使用原生能力或 React Native，不能把 PWA 当作最终“丝滑移动体验”的证明。

### 9.4 Secure Relay

主机只建立出站连接。中继负责发现、路由、密文短期存储和通用 Push，不持有内容密钥。高级用户可以自托管，企业可以选择自有中继或私网模式。

## 10. 护城河假设

语言和模型接入都容易被追平。更有价值的积累是：

- 经历弱网、后台挂起和多设备竞争后仍正确的事件协议与状态机。
- 对 shell、文件、网络和 Git 操作的移动审批呈现与风险分类。
- 不同模型和 Agent runtime 到统一 Session Protocol 的适配层。
- 长会话、断线和权限行为的化名化可靠性数据，不采集代码内容。
- 开源 runtime 带来的分发、审计和自托管生态。

这些仍是假设。若用户只把产品当通知工具，不愿迁移 CLI，也不愿为连接能力付费，独立 runtime 的护城河不会成立。

## 11. 商业模式假设

首年优先验证使用和留存，不急于锁定价格。建议的价值分层如下：

| 版本 | 可能包含 | 收费逻辑 |
| --- | --- | --- |
| Community | CLI、Runtime、本地 Web、自托管中继、BYOK | 免费开源，建立信任和分发 |
| Personal Pro | 托管中继、Push、多设备、较长密文历史、可靠性 SLA | 候选价格为每月 12 至 20 美元，需做支付意愿测试 |
| Team | 组织设备、策略、审计、SSO、托管或自有密钥 | 候选价格为每席每月 25 至 40 美元 |
| Enterprise | 数据区域、私有中继、合规、支持和策略集成 | 年度合同 |

模型 Token 默认由用户向 Provider 付费。Nomad 不在早期补贴推理，也不把模型差价作为主要收入。

开源许可需在技术原型通过后单独决策。倾向 Apache-2.0，因为它比 MIT 多一层明确专利授权；若商业模式要求部分服务端闭源，应提前划清协议、runtime 和托管控制面的边界。

## 12. 成功指标

### 12.1 北极星指标

每周至少远程推进一个 Turn 的用户数。

一次“远程推进”只有同时满足以下条件才计数：

- Turn 在 CLI 中启动，Host 在远程操作发生时保持在线。
- 用户从另一台设备发送 reply、纠偏指令或允许一次。
- Host 明确接纳该操作，随后产生新的模型完成消息、工具开始/完成、有效 diff 变化或 Turn 完成事件。Ack、`message.accepted`、presence 和 metadata 更新不算进展。
- Turn 最终进入 Completed、Cancelled 或 Failed，没有未解释的事件缺口。`OutcomeUnknown` 单独计为安全异常，不计入北极星指标。

Stop 和 deny 可能很有价值，但它们计入“远程止损 Turn”，不计入北极星指标。团队同时报告每个 Turn 的权限请求数，防止通过制造更多弹窗抬高使用量。

### 12.2 输入指标

| 环节 | 指标 | Beta 目标 |
| --- | --- | --- |
| 激活 | 安装到完成首个有效 CLI 任务的中位时间 | 少于 10 分钟 |
| 配对 | 首次扫码到手机可见机器 | P50 少于 30 秒，成功率至少 95% |
| 使用 | 周活用户中完成至少一次跨端操作的比例 | 至少 35% |
| 价值 | 从 Push 打开到解除常规阻塞的中位时间 | 少于 15 秒 |
| 留存 | 已完成跨端闭环用户的第 4 周留存 | Alpha 报告绝对人数；至少 60 名激活用户后再使用 40% 目标 |
| 可靠性 | 自动故障注入恢复 | 足量样本后至少 99.5%；真实用户流量报告成功/失败次数 |
| 安全 | 重复执行、错误绑定审批、Push 泄露内容 | 0 起事故 |

Beta 目标用于做 go/no-go，不是对外 SLA。样本量不足 30 人时只看行为和访谈，不对百分比作过度解释。

## 13. 当前关键假设

| 假设 | 当前证据 | 信心 | 最近验证方式 |
| --- | --- | --- | --- |
| CLI 用户会频繁离开长任务 | 竞品投入和现有 workaround 是供给侧信号，缺少本产品一手行为数据 | 中低 | 15 次情境访谈加一周日志研究 |
| 用户更需要结构化控制而非完整终端 | GitHub Mobile、Claude Remote 和 Codex Remote 都采用任务 UI | 中高 | 可点击原型与远程终端对照测试 |
| 模型无关和 local-first 足以促成迁移 | 竞品能力存在空档，但迁移成本未知 | 中低 | OpenCode 用户封闭测试和迁移访谈 |
| 用户愿意安装 daemon 并配对手机 | Happy、Tailscale 等有先例 | 中 | 安装漏斗和可用性测试 |
| E2EE 会影响选择或付费 | 开发者关心代码隐私，但实际支付意愿未知 | 低 | 隐私方案排序和价格敏感度访谈 |
| Rust 内核能带来显著本地收益 | 有长会话内存和启动热点证据，尚无本项目基准 | 低 | 固定 fixture 的 Rust/现有实现对照基准 |
| 独立 runtime 比只做 companion 更有长期价值 | 可控制协议和性能，但开发成本大 | 低 | 比较 adapter 原型的留存与迁移意愿 |

## 14. 明确不做

- 不在首版做完整移动 IDE、调试器或 LSP 界面。
- 不默认开放任意远程 shell。
- 不允许锁屏通知直接批准命令。
- 不让手机设置永久全局 auto-approve。
- 不把公开分享、社交会话或多人聊天作为增长手段。
- 不在验证前复制 OpenCode 的 75+ Provider、插件系统和全部 HTTP API。
- 不宣称电脑休眠、关机后本地任务仍然运行。
- 不把“Rust 重写”作为融资或营销中的性能结论。
- 不承诺与 OpenCode 的名称、配置、数据库或插件二进制兼容。

## 15. 一年后希望看到的状态

一年后的合理结果不是“功能超过所有 Agent”，而是：一批高频 CLI 用户愿意每天把任务交给 Nomad；跨端恢复和审批没有出过严重事故；他们离开电脑后仍自然地打开手机继续推进；自有 Runtime 在真实长会话中比基线更省资源；一部分用户愿意为托管连接和可靠 Push 持续付费。

如果跨端操作没有进入每周习惯，团队应收缩为开源本地 Runtime 或停止项目，而不是用更多模型和工具掩盖问题。
