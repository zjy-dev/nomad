| 字段 | 内容 |

## 1. 招募筛选

筛选问卷只用于判断资格，不向候选人描述预期答案。

1. 过去两周，你使用过哪些 CLI code agent？各使用多少天？
2. 过去两周，有多少次单个任务运行超过 10 分钟？
3. 最近一次长任务是什么时候？任务运行时你是否离开过电脑？
4. 离开后你如何知道任务状态，或如何继续操作？
5. 你是否使用过 SSH、tmux、远程桌面、移动终端、通知脚本或 auto-approve？
6. 你的主要开发电脑和手机平台是什么？
7. 是否愿意在项目提供的可丢弃仓库和临时账户上参加 45 分钟测试？
8. 是否愿意一周内进行第二次无主持测试？此题不作为入选硬门。

有效高频样本必须满足：每周至少三次 CLI agent 使用、最近两周至少三次 10 分钟以上任务、能描述一个最近真实事件。

## 2. 情境访谈脚本

### 2.1 开场

说明研究产品工作流，不测试参与者能力；允许随时结束；不要在共享材料中展示真实代码、客户信息或凭据。征得记录同意后开始。

### 2.2 最近行为

1. 请从最近一次超过 10 分钟的 Agent 任务开始，按时间顺序讲发生了什么。
2. 你当时为什么离开或切换注意力？离开了多久？
3. 你如何判断 Agent 在工作、等待、失败还是完成？
4. 有没有因为需要回答或权限而停住？你多久后发现？
5. 你最终如何继续：回电脑、SSH/tmux、远控、放宽权限、放弃还是重开？
6. 这个过程损失了什么：等待时间、上下文切换、风险、重复执行或焦虑？
7. 如果工具只发完成通知，能解决多少？还缺什么？
8. 如果手机只能查看、reply、deny 和 Stop，哪些情况有用，哪些必须有 allow 才有用？
9. 哪些信息缺失时你绝不会在手机上处理？
10. 你使用第一方 Remote 或通用远程终端吗？为什么仍会或不会换工具？

避免问题：不问“你会不会使用 Nomad”“你愿意付多少钱”“这个功能酷不酷”。先记录事实，再在最后展示概念。

## 3. 一周日记模板

参与者每次遇到事件后尽快记录，不在周末回忆补写。一天没有事件也记录 `none`。

```text
日期和大致时间：
使用的 Agent 类别：
任务大类：
任务已运行多久：
是否离开电脑，多久：
离开时你认为它处于什么状态：
回来后实际状态：
是否等待回答/权限，等待多久：
你采取了什么办法：
是否造成重复、风险或返工：
如果手机能查看/reply/deny/Stop，能否避免这次成本：
还有什么信息必须在电脑上看：
```

研究员不得要求粘贴终端原文、Prompt、路径、diff 或代码。

## 4. 结构化 UI 对照任务

每名参与者以平衡顺序体验结构化 UI 和移动终端截图/原型，避免顺序偏差。

| Task | 给用户的任务 | 通过条件 | 观察重点 |
| --- | --- | --- | --- |
| T1 | “你离开电脑后打开手机。告诉我任务是否需要你，以及最后在做什么。” | 10 秒内回答正确 | 是否把 Online 误认为正在运行 |
| T2 | “Agent 在等待一个问题。回复使用 SQLite，并确认消息是否真正到达 Host。” | 回复一次且正确解释阶段 | 是否把 Relay received 当执行完成 |
| T3 | “Agent 请求执行一个你不希望发生的操作。阻止它。” | deny 或 Stop，不寻找 Allow | Host 事实是否足够 |
| T4 | “Agent 方向错了，立即停止当前 turn。” | 正确 Stop 并等待已取消 | 是否误判 ACK 为 Cancelled |
| T5 | “判断改了哪些文件，以及你是否需要回电脑。” | 识别文件、规模和不确定项 | 示例/非权威数据不得出现 |
| T6 | “网络刚恢复。现在能否安全发送操作？” | Stale 时不操作，Live 后才继续 | 状态可解释性 |

每题记录完成、时间、求助、错误、信心（1-5）和原话。高风险误操作立即停止该任务。

结束问题：

- 哪个界面应该作为默认入口？为什么？
- 哪三条信息最影响你做决定？
- 哪些技术字段应该隐藏，哪些应保留在详情？
- 没有 Allow 的情况下，你还会在哪些场景使用？
- 哪一步让你最不信任系统？

## 5. Pilot 无主持任务单

参与者只收到以下目标和用户级帮助文档，不收到 event/contract/内部架构说明。

1. 运行预检，按提示修复环境。
2. 启动固定测试任务。
3. 用手机扫码并确认两端比对码。
4. 离开电脑后，判断任务状态。
5. 回答一次 Agent 问题。
6. 拒绝一次权限请求或停止当前 turn。
7. 查看这次任务的文件改动。
8. 在测试人员触发网络中断后，判断何时可以继续操作。
9. 完成清理。

求助规则：研究员先问“你预期在哪里找到答案”，再提供最小提示；每次提示计一次 help，不把被指导完成记为无主持成功。

## 6. 测后访谈

1. 哪个时刻最像你真实工作，哪个最不像？
2. 哪个动作真正省去了回电脑？
3. 哪个状态或结果让你不确定？
4. 如果今天移除这个工具，你会回到什么办法？
5. 没有 Allow 对价值影响多大？请用具体场景说明。
6. 你愿意一周内独立再做一次吗？为什么？
7. 你会允许它接触真实仓库吗？在此之前需要什么证据？

不在本阶段询问抽象付费意愿。可以记录用户主动提到的价格，但不计商业验证。

## 7. 研究问题编码

| Code | 含义 | 示例 |
| --- | --- | --- |
| NEED-FREQ | 问题频率不足 | 一个月才离桌一次 |
| ALT-GOOD | 现有替代已足够 | tmux 完全满足 |
| INFO-MISSING | 缺少决定信息 | 看不到 cwd 或改动 |
| STATE-CONFUSED | 状态理解错误 | 把 Online 当 Running |
| TRUST-ACTION | 不信任操作绑定/结果 | 不确定 Stop 是否生效 |
| TRUST-DATA | 不信任数据边界 | 担心 Relay 看代码 |
| INSTALL | 安装或版本问题 | 不知道如何修 OpenCode 版本 |
| PAIR | 配对问题 | 比对码含义不清 |
| RELIABILITY | 连接/恢复/重复问题 | 恢复后仍 Stale |
| SCAFFOLD | 实验环境问题 | 临时账户过期 |
| VALUE-REPLY | reply 产生价值 | 不必回桌回答 |
| VALUE-STOP | deny/Stop 产生价值 | 及时止损 |
| VALUE-DIFF | Changes 产生价值 | 判断是否值得回桌 |
| REQUIRE-ALLOW | 无 Allow 就无价值 | 主要阻塞都是低风险批准 |
| NOTIFICATION-ONLY | 完成通知已足够 | 不会在手机交互 |

每个事件可以有多个 code，但失败分型只选择一个首要原因。

## 8. 研究完成检查

- 配额完整，排除无效样本有理由。
- 最近行为与概念反馈分开分析。
- 反例和退出用户得到同等篇幅。
- 原始次数、中位数和 P95 可复算。
- 没有把“愿意试试”计成使用或留存。
- 没有真实源码、Prompt、命令、路径、diff 或凭据进入研究资产。
- 结论同步到 [Pilot 计分卡](pilot-scorecard.md) 和 decision log。
