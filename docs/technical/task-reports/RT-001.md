## 1. Purpose

This task freezes the preregistration contract for the Nomad native runtime spike. Before any engine code is written or any measurement is taken, we lock in:

- The workload set and its weights.
- The comparison baseline and its SQLite PRAGMA.
- The fixture set and its hashes.
- The hardware manifest schema.
- The go/no-go and nonregression gates.
- The measurement provenance and hash rules.

Nothing in this report is a result. No runtime code was written. No measurement was taken. The intent is to prevent post-hoc baseline shopping, silent fixture changes, and gate movement after evidence exists.

## 2. Workload set

Five workloads are preregistered. Weights reflect engineering priorities, not claims about production frequency.

| ID | Name | Weight | Pass condition | Gate |
| --- | --- | --- | --- | --- |
| ws-cold-start | Weighted cold start | 0.30 | p50 <= 150 ms AND p95 <= 300 ms | no regression; budget +20% |
| ws-recovery-100k | 100k-event recovery | 0.25 | p50 <= 5 s; peak RSS <= 512 MiB; query p95 <= 2 ms (last-1k) / 20 ms (cursor resume) | runtime must beat baseline by 2x OR reduce peak RSS by 40% |
| ws-append-durable | Durable append throughput | 0.20 | throughput >= 5000 events/s; p95 <= 1 ms | no regression; budget +10% |
| ws-long-session-rss | Long-session RSS | 0.15 | peak RSS <= 384 MiB at hour 8; no net growth from hour 4 to 8 | runtime must reduce peak RSS by 40% vs baseline |
| ws-sidecar-ipc | Sidecar IPC | 0.10 | IPC overhead < 5% of end-to-end command latency | strict nonregression; any degradation must be explained |

Weights sum to 1.00 (0.30 + 0.25 + 0.20 + 0.15 + 0.10).

## 6. Go/no-go gates

### 6.1 Hard gates (pass/fail)

| Gate ID | Condition |
| --- | --- |
| G-001 | 100% conformance with preregistered fixture set |
| G-002 | ws-recovery-100k completes without data loss or unknown gaps |
| G-003 | ws-long-session-rss shows no net RSS growth between hour 4 and hour 8 |
| G-004 | All seq values strictly monotonic; no gap > 1 seq silently skipped |
| G-005 | ws-cold-start p95 <= 300 ms |
| G-006 | ws-append-durable throughput >= 5000 events/s, p95 <= 1 ms |
| G-007 | ws-sidecar-ipc overhead < 5% of end-to-end command latency |

### 6.2 Comparative gates

| Gate ID | Condition |
| --- | --- |
| CG-001 (2x gate) | ws-recovery-100k runtime is 2x or faster than baseline OR ws-append-durable runtime is 2x or faster than baseline |
| CG-002 (40% gate) | ws-long-session-rss peak RSS is >= 40% lower than baseline OR ws-cold-start peak RSS is >= 40% lower than baseline |
| CG-003 (nonregression) | No workload regresses beyond its budget |

### 6.3 Per-workload nonregression budgets

| Workload ID | Allowed regression |
| --- | --- |
| ws-cold-start | +20% |
| ws-recovery-100k | +15% |
| ws-append-durable | +10% |
| ws-long-session-rss | +15% on peak; +10% on slope |
| ws-sidecar-ipc | strict nonregression (0%) |

### 6.4 Decision rules

- **GO:** All hard gates pass + at least one of CG-001/CG-002 passes + CG-003 passes for every workload.
- **NO-GO:** Any hard gate fails OR both CG-001 and CG-002 fail OR CG-003 fails for any workload.
- **CONDITIONAL GO:** All hard gates pass + CG-003 passes + at least one comparative gate nearly passes (>= 1.6x or >= 35%) + written mitigation plan attached.

## 7. Out of scope

- Source-build comparison against release binaries.
- Manually dropping high-weight workloads after measurement.
- Selecting a different OpenCode release post-hoc.
- Combining cold-start and recovery into one number.

## 11. How to regenerate

If the preregistration contract changes (new workload, changed baseline, changed PRAGMA), run:

```
python3 runtime-spike/scripts/compute_hashes.py
python3 runtime-spike/scripts/gen_fixtures.py
python3 runtime-spike/scripts/hardware_manifest.py --output runtime-spike/hardware/capture.json
python3 runtime-spike/validators/check_preregistration.py
python3 runtime-spike/validators/check_fixtures.py
python3 runtime-spike/validators/check_hardware.py
python3 runtime-spike/validators/check_pragma.py
```

All prior raw measurements must be invalidated via the `superseded-by` protocol in `provenance.md` section 5.
