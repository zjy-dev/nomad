## Outcome

Implemented retention, capacity, and backpressure controls: TTL-based frame expiry, ACK window cleanup, per-device mailbox capacity enforcement, and a background worker for periodic cleanup. Overflow errors are explicit — they do not silently drop or misreport as "delivered."

## Changed

- `relay/worker.go` — Retention worker for periodic cleanup.
  - `Worker` struct with configurable interval and stop channel.
  - `Run(ctx)` — ticker-driven loop calling `cleanup()` on each interval.
  - `cleanup()` — calls `CleanupTTL()` and `CleanupAcked()`, logs removal counts.
  - `Stop()` — signals graceful shutdown.
- `relay/mailbox.go` — Retention and capacity methods.
  - `CleanupTTL()` — deletes frames where `ttl <= now`, returns `rowsAffected` count.
  - `CleanupAcked()` — deletes frames where `acked=1 AND created_at <= (now - ACKWindow)`, returns count. `ACKWindow = 720h` (30 days).
  - `StoreFrame()` — capacity check: counts unacked frames for device, rejects with `ErrCapacityExceeded` if `>= MaxMailboxFrames` (1000).
  - Rate limiting: `rateLimit()` maintains per-device sliding window of frame timestamps, rejects with `ErrFrameRateLimited` if `>= MaxFramesPerSecond` (10).
  - Capacity error → HTTP `503 Service Unavailable`, rate limit → `429 Too Many Requests`, frame too large → `413 Request Entity Too Large`.
- `relay/server.go` — HTTP error mapping for backpressure conditions.
  - `handleFrame` maps error types to correct HTTP status codes so callers can distinguish capacity exhaustion from other failures.
- `relay/protocol_test.go` — tests for retention and capacity:
  - `TestTTLExpiry` — frame stored with zero TTL → not deliverable; `CleanupTTL()` removes it (returns count=1).
  - `TestCapacityExceeded` — `MaxMailboxFrames` (1000) frames stored; next frame rejected with `ErrCapacityExceeded` or `ErrFrameRateLimited` (rate limit may kick in first).
  - `TestMaxFrameSizeRejected` — frame at exactly `MaxFrameSize` passes; `MaxFrameSize+1` rejected.

## Decisions and deviations

- Retention worker interval is configurable via `-cleanup` flag (default 1 minute). The worker runs in a goroutine and is stopped gracefully on SIGINT/SIGTERM.
- TTL is stored as Unix timestamp (integer) in SQLite, not a duration. `DefaultFrameTTL = 168h` (7 days) from creation time.
- ACK cleanup window (`ACKWindow = 720h` = 30 days) is hardcoded — tunable in future iterations but not exposed as a CLI flag.
- Capacity limit (`MaxMailboxFrames = 1000`) is per-device, not global. This prevents a single device from exhausting the server while allowing other devices to operate.
- Rate limit is a sliding window (timestamps in the last 1 second), not a token bucket. This is simpler and sufficient for the reference implementation.

## Security and privacy

- Deletion idempotency: `CleanupTTL` and `CleanupAcked` use simple DELETE statements — safe to call multiple times or concurrently.
- Content-type agnostic: backpressure is based on frame count and payload size, not content type or payload interpretation. The relay cannot be tricked into treating certain payloads as "priority."
- Explicit error reporting: capacity exhaustion returns `503` distinct from rate-limit `429` and payload-too-large `413`. Callers can distinguish these and take appropriate action (retry later, reduce rate, reduce size).
- No silent drop: when capacity is exceeded, the frame is NOT stored and an error is returned immediately. The caller knows the frame was rejected — there is no silent data loss.
- Privacy-safe logs: cleanup log messages contain only removal counts, not frame content or device identity beyond counts.
- Race-condition safety: `go test -race` passes with no data races detected (1.985s).
